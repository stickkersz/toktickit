## How review worked in Lab 3

Lab 3 used the same Issue, feature branch and Pull Request flow as Lab 2, with every feature branch merged into `lab3-staging` and one release Pull Request from `lab3-staging` into `main`. One thing changed: in Labs 1 and 2 reviews were plain comments, and from Lab 3 on every review is a formal GitHub verdict, **Request changes** when something has to be fixed and **Approve** when nothing does. Every Pull Request was merged after an Approve, and every change reached `main` through one, with a single exception at the very end: after the release, two final rechecks against the labsheet found evidence gaps, four small UI details, Attachment preview, removal of the old selector's stored value and two missing rules, and those fixes were pushed directly to `main` in a few commits, without a Pull Request or peer review, because the submission deadline was close. They are listed in `docs/lab-03/tests.md` section 6 under "Labsheet compliance pass". In all but one the Approve was on the commit that was merged. The exception is my partner's #57: I approved its fix at `5f32385`, they then pushed `0ec55fb`, which only updated their own `reviewer.md`, and I checked that commit and said so in a Pull Request comment before merging rather than submitting a second review.

Each round below is a real GitHub review on the actual diff. When changes were requested, the author answered with a fix commit and a short comment saying what changed, and the reviewer rechecked that exact commit before approving. Pull Requests approved on the first review, such as my #49, #50, #53 and #56 and my partner's #55 and #56, needed no fix commit. Every quote is taken from the review as posted.

Two patterns repeated across both repositories. Integer ids above the 32-bit range crashed my partner's routes three times (#53, #54 and its follow-ups), and writes that could land out of order or half applied came up on both sides: my #51 status write and my #57 password change, and their #52 comment form, where a slow load overwrote a post that had already finished. The password change is the clearest case: on the same day, my partner found that my Change Password could leave the old sessions alive after a failure, and I found that theirs never ended the other sessions at all. Both were fixed the same way, with the update and the revocation in one transaction. Seeing the same class of bug from the other side made me look for it in my own code sooner.

## How review comments were given and received

Both directions followed the same rules. Read the actual diff, not the Pull Request description. Cite the real `file:line`. Run the suites when a count is claimed. Never approve a fix from its commit message; recheck the fix commit itself. Findings were kept short and casual, the way classmates talk on a Pull Request, and each one asked for a test that fails without the fix, so that "fixed" could be checked rather than taken on trust.
